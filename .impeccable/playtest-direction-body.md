# PlayTest ID platform surfaces

Scope and mode: responsive web UI for the Developer, Tester, and Admin workspaces. Operate.

Audience and task: developers configure Android test cycles and monitor cohorts; testers complete eligible daily missions and submit evidence; admins manage exceptions, payments, reports, rewards, and audit. The PRD's listed product KPIs are the success measures; production targets and business values remain configurable and undecided.

Content and constraints: Indonesian product terminology; all displayed operational values and accounts are explicitly labeled demo. No real authentication, upload, payment, payout, or backend behavior is in this frontend scope. Protect role boundaries in the UI and expose loading, empty, error, blocked, and success states. Desktop-first developer/admin, mobile-first tester.

Chosen direction: Buku Cue Stage Manager. A connected testing cycle is a run sheet: tabbed project index, daily mission cues, and traceable issue slips. Keep actual product labels. Warm paper and dark ink form the ground; coral marks active/attention, teal marks complete. Use an unambiguous workhorse sans for reading and a restrained mono only for identifiers and measured values. No theatrical ornament or generic equal-card dashboard.

## Direction contract

THESIS: PlayTest ID is the run sheet for a real Android testing cycle: each role sees the next cue, its status, and the evidence that lets the cycle advance. Refuse the category-default dashboard of interchangeable KPI cards.

OWN-WORLD: Tabbed run sheets, task rows, and incident slips organize the interface. Use warm paper fields, dark ink, coral for active or urgent cues, and teal for verified completion. Strong dividers and asymmetric editorial columns distinguish the active run from its audit trail. Keep sans-serif reading text and reserve monospaced type for IDs, versions, and measured values.

STORY: Developers prepare a test and track recruitment through feedback; testers pick up one clear mission at a time; admins see exceptions and their audit trail. The signature interaction is “advance the cue”: completing or reviewing a row changes the run sheet's next action and visible progress, using local demo state only.

FIRST VIEWPORT: On desktop, a persistent role-aware rail sits left; the main header names the workspace and puts “Buat pengujian” at the top right. A horizontal run-sheet strip shows the cycle stages beneath it. The first content band pairs a detailed active-project run sheet and tester progress table with a narrow incident/activity column. Do not lead with a hero metric. On mobile Tester Home, place the active test and its next mission first, with day progress and reward state visible before secondary activity; bottom navigation stays reachable.

FORM: Assigned form 3 of 7, Buku Cue Stage Manager. Concept seed key: be7db898. Apply the cue sequence, tabbed index, and incident-slip grammar across all three role areas and their distinct desktop/mobile layouts.
